# Readraft：竞争定位与优势边界

> 文档状态：产品基线
>
> 更新日期：2026-08-05
>
> 正式名称：**Readraft**。市场上另有名为 `NovelAI` 的产品；
> 两者没有隶属、授权或合作关系。
> 本文用“本项目”指当前代码，用“NovelAI（现有产品）”指对方。

## 1. 一句话定位

> **本项目不是一个更会续写的聊天框，而是一套让长篇故事可规划、
> 可确认、可追溯、可恢复的创作系统。**

更准确的品类是：

> **作者控制的长篇叙事工作台。**

它把长篇创作视为持续演化、需要治理的故事状态，而不只是越来越长的
一段文本：

```text
作者意图
  → Agent 检索与受控修改
  → 不可变正文版本 / 经确认的作品资料
  → main HEAD
  → Story Delta
  → 确定性状态重放
  → 下一章受约束的创作上下文
```

核心边界是：**模型可以直接执行作者明确要求的修改，但只能通过受控
版本提交改变正文；未来计划和模型分析不能自行冒充已经发生的事实。**

## 2. 公平对比

| 代表产品 | 对方当前擅长什么 | 本项目的实现差异 | 对方明显更强的地方 |
|---|---|---|---|
| **Novelcrafter** | Codex、规划视图、写作、聊天、版本历史、协作和完整项目导出；可连接 300 多个模型及本地模型 | 不只把资料送进提示词，而是把“候选—确认—正史—状态重放”设为服务端状态机；异步结果带冻结基线和指纹，过期结果不能覆盖新工作 | 模型和供应商覆盖、协作、导入导出、交互成熟度与用户生态 |
| **Sudowrite** | Story Bible 从构思、梗概、人物、世界和提纲推进到场景与正文；另有 Canvas、插件、系列共享和移动端 | 进一步区分“未来规划”和“已经发生的正史”；正文确认后生成 Story Delta，再确定性重放人物知情、关系、伏笔、物品和剧情线状态 | 灵感与散文辅助、低学习成本、视觉规划、插件、移动端与系列体验 |
| **NovelAI（现有产品）** | 专用生成体验、模型和采样控制、Memory、Author's Note、Lorebook 条件注入、上下文查看器、脚本扩展与可移植故事导出 | 重点不在 token 级生成控制，而在虚拟作品工作区、可撤回 HEAD、结构化计划、证据化故事状态和跨章连续性 | 模型与采样控制、流式生成、Lorebook 条件系统、脚本生态和成熟导出 |
| **Scrivener** | 长文拆分、研究资料、软木板、Outliner 和 Word/PDF/Final Draft 等成熟编译导出 | 让确认计划、人物知情、因果、伏笔和正史状态直接参与生成前约束与生成后审计，而不只由作者手工维护资料 | 纯写作体验、项目组织、排版编译、跨平台桌面体验和长期稳定性 |
| **Plottr** | 可视化时间线、情节线、场景卡、Story Bible、模板、系列规划，以及 Word/Scrivener 导出；Pro 版支持云同步和协作 | 任务卡中的推进线、必做事件、伏笔和钩子必须落到具体场景；缺失覆盖时服务端阻止确认，后续正史变化还会触发影响检查 | 时间线可视化、拖拽规划、模板、系列视图、同步、离线与协作 |

这里最接近本项目的是 **Novelcrafter**。因此，“有资料库、能规划、
能聊天、能保存版本”都不能算本项目的独特优势；成熟产品已经具备这些
能力。

## 3. 当前真正成立的优势

### 3.1 作者确认不是界面提示，而是数据边界

设定、全书蓝图、剧情线、章节任务卡和 Story Delta 都有明确确认边界。
正文写入不需要另一套“候选晋升”，而是直接创建可撤回的不可变版本并
推进 main HEAD；未确认资料不能进入下游权威上下文。

### 3.2 长篇故事可以确定性重放

正史正文不是简单追加到提示词。章节确认后，系统把变化投影为
Story Delta，并按顺序重放人物状态、关系、物品、知情边界、剧情线、
伏笔和故事时间。相同正史输入会得到相同状态，问题可以定位到具体
章节和证据。

### 3.3 异步 AI 结果有基线和保质期

全书方案、滚动结构、场景计划、因果建议和长期沙盘在发起时冻结当前
计划、正史与结构指纹。作者在等待期间继续修改作品后，旧结果会被
识别为过期，而不是静默覆盖较新的决定。

### 3.4 规划能落到可执行节拍

章节任务卡中的推进线、必做事件、伏笔和章末钩子可以映射到具体场景
节拍，让 Writer 获得可执行的章内结构。节拍只是规划数据；正文仍通过
统一 compose 管线生成并提交为一个章节 HEAD，不维护逐场景正文仓库。

### 3.5 因果建议必须带证据和决策门

跨章因果候选引用冻结的章节、事件和计划证据，并分别检查事实、人物
知情、时间、世界规则和连续性。长期影响先进入只读三分支沙盘，再由
作者逐章编辑、接受或拒绝，不会直接改写未来任务。

### 3.6 正文提交、质量建议与风格学习彼此分离

正文创作统一推进可撤回 HEAD；连续性和文风检查只给出证据化修改建议，
不设置另一套硬门禁。参考作品只沉淀为带证据和原创性边界的抽象技法卡；
作者自己的手工改稿也要经过差异证据定位和确认后，才成为后续写作偏好。

### 3.7 本地数据可检查、可迁移、可恢复

项目使用 SQLite 和本地正文文件，个人模型凭据由作者提供。完整备份
会把数据库路径改写为可迁移标记，逐文件校验数据库、正文、历史版本
和参考资料；恢复前还会自动保留当前数据的安全归档。

## 4. 还不能当作优势宣传的部分

- 当前正式接入 DeepSeek、OpenCode Go、自定义 OpenAI、OpenAI、Gemini
  和 Ollama，但模型目录、参数映射和真实供应商验收广度仍远低于
  Novelcrafter 和 NovelAI（现有产品）。
- 统一工作台已经覆盖正文、作品资料、分析、版本和对话，但部分复杂
  结构化结果仍使用专用审核页；尚未经过真实新用户的完整可理解性测试。
- 自动化测试证明结构、权限和状态门禁，不证明真实模型输出质量；
  固定样稿的多 Provider 真实验收仍需完成。
- SQLite、单进程和单后台 Worker 适合个人使用，不是多人规模优势。
- 五类语义预检能提供证据和决策门，不能证明自然语言事实或因果绝对
  正确。
- 当前没有成熟移动端、协作、可视化时间线、DOCX/EPUB 排版和发布
  生态。
- “本地优先”和“作者自带 Key”是隐私及成本取舍，不天然等于更好的
  创作体验。

因此，现阶段最可信的表达是：

> **其他工具通常优先帮助作者更快地产生和组织文本；本项目优先帮助
> 作者在作品越来越长之后，仍然知道什么已被确认、为什么成立、改动
> 会影响哪里，以及下一章应在什么约束下继续。**

## 5. 下一步如何证明优势

1. 用同一套 3–5 章样稿，分别验证规划、创作、修改、版本与记忆链，
   记录结构失败率、耗时、token、费用和人工评分。
2. 已完成规划、正文、版本、分析和记忆入口整合及桌面/手机宽度
   验收；下一步让 3–5 位未接触项目的作者不看说明完成一次闭环，
   记录卡点和误操作。
3. 设计“修改旧章后继续写”的对照任务，验证冻结基线、下游自动失效和
   状态重放是否真实减少连续性错误。
4. 已完成一次真实数据完整备份和异地恢复演练；下一步增加定时备份、
   保留策略和周期性恢复抽检。
