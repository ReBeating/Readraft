# Readraft 核心写作与拆书实现计划

> 更新日期：2026-08-05
> 本文只描述当前正式架构和下一阶段实现，不保留已删除流程的兼容说明。

## 1. 不可破坏的原则

1. 每部作品只有一个可写 `main`；Tag 只读。
2. 每章只有一个 `main HEAD`。保存、AI 创作、撤回和恢复都创建新的不可变版本，
   再原子推进 HEAD。
3. 自动暂存不是版本；暂存必须绑定读取时的 HEAD，过期后不能覆盖新内容。
4. 计划、未确认设定、模型建议和参考书观察都不是既有故事事实。
5. Agent 只访问 `book/` 虚拟工作区，不访问服务器文件系统或裸数据库。
6. 所有写入在执行时再次校验用户、作品、`main`、能力和 revision。
7. 长篇正文只由统一纯文本写作管线生成；结构化工具不能把 JSON、推理或审计说明
   写进正文。
8. 质量检查是建议，不是保存门禁。系统不设置统一字数硬下限，也不维护逐场景正文链。

## 2. 当前正式数据流

```text
作者请求
  -> 对话持久化与轻量意图边界
  -> Provider 原生工具 Agent
  -> 在 book/ 中 glob / read / grep / search 取得必要证据
  -> edit / write / patch，或 create / compose / series
  -> 领域层复核权限与 revision
  -> 创建不可变版本并原子推进 main HEAD
  -> 失效旧分析与 Story Memory
  -> 异步重建与后续章节待复查标记
```

模型可以在一轮中连续选择工具。服务端不预编排固定工具链，不设置默认总回合或工具
预算；仅保留重复无进展熔断、并发校验和可撤回提交等运行边界。

作者明确要求“只讨论”或“不要写入”时，Agent 只能读取和回答。作者明确要求创建、
续写或修改时，Agent 应在写入前取得必要证据并直接执行，不在生成完成后追加一次
无意义确认。

## 3. 版本和存储模型

### 3.1 正文

| 对象 | 作用 | 可变性 |
| --- | --- | --- |
| `novel_chapters.head_version_id` | 当前章节唯一 HEAD 指针 | 事务中推进 |
| `novel_chapter_versions` | 内容路径、哈希、父版本、来源和时间 | 不可变 |
| `novel_chapters.content_path` | 可从 HEAD 重建的读取缓存 | 非权威 |
| chapter edit buffer | 崩溃恢复，绑定 base HEAD | 可覆盖、有限额 |
| work Tag manifest | 固定全书章节版本与作品资料 | 不可变、只读 |

SQLite 触发器拒绝跨章节 HEAD 和跨章节父版本。`readraft-doctor` 校验数据库、文件、
哈希、字符数、缓存、暂存、导入章节和 Tag 清单；`--repair` 只能修复非权威缓存，
`--prune-orphans` 才会显式删除当前数据库拥有目录中的无引用文件。

章节历史首屏只读取最近版本，需要更早内容时使用分页 `history`/版本页。Agent 工作区
只预载每章最近有限数量的历史条目，避免长项目启动时把全部版本读入内存。

### 3.2 作品资料与故事状态

作品资料分为五类：

- 作品概览：书名、题材、故事承诺、目标读者、主题、核心吸引力与结局边界；
- 世界：背景、规则、势力、地点、物件和术语；
- 人物：身份、目标、动机、矛盾、秘密、关系、声音与人物弧；
- 剧情与结构：蓝图、长期剧情线、分卷、未来章节骨架、任务卡和场景节拍；
- 叙事与文风：视角、时态、声纹、偏好、禁用表达和已绑定技法。

设定与未来计划进入写作包前必须越过各自的确认边界。Story Memory 来自当前 HEAD 的
证据化提取和作者确认，保存人物状态、关系、地点、物品、知情、剧情线、伏笔、时间和
事件因果。HEAD 改变时，旧投影失效并按章节顺序重放。

## 4. Agent 工具边界

### 4.1 基础工具

- `glob`：发现虚拟资源；
- `read`：分段读取并取得 revision；
- `grep`：准确文本或正则检索；
- `search`：模型扩展概念后的中文稀疏召回，命中后仍需 `read`；
- `diff`：比较已读取的正文、历史或笔记；
- `edit`：单资源精确替换；
- `write`：新建或整体更新小型结构化资料，不能覆盖章节正文；
- `patch`：同一提交边界内原子应用一个或多个精确替换；
- `delete`：只删除作者明确点名且允许删除的结构化资源；
- `restore`：把不可变历史复制成新的 HEAD；
- `web_search` / `web_fetch`：只读外部资料，拒绝本机、内网和非文本目标。

`edit` 是单个精确替换，`patch` 是一组“全成或全败”的精确替换。章节、作品设定和
故事规划不能混在同一个 patch 中。

### 4.2 小说领域动作

- `create`：在 main 末尾建立新章节并切换当前范围；
- `compose`：生成、续写或大范围重写当前章节；
- `series`：作者明确要求时连续创作多章，逐章独立推进 HEAD 并支持断点恢复；
- `task`：把明确资源交给无工具、无写权限、不能递归委托的专项模型做只读核对。

`write` 表示受控保存小型结构化资源，`compose` 表示写作行为。两者不能合并：如果让
通用 `write` 接受长篇正文，Agent 会把正文塞进工具 JSON，导致长度、转义、流式显示和
失败恢复都变差。

## 5. 正文写作质量

`prose_craft.py` 是唯一通用写作规则来源。写作包只包含本轮真正需要的材料：

1. 作者原始目标和不能改变的事实；
2. 作品承诺、视角、声纹和启用的抽象偏好；
3. 本章任务卡与被选中的长期剧情线；
4. 当前章、相邻章节尾部和检索到的早期 Story Memory；
5. 涉及人物、地点、规则、物件和知情边界；
6. 对应操作的局部文本、预期变化和结束条件。

通用写作规则强调可感知的场景、人物行动与选择、因果推进、具体空间、信息控制、
不同人物的语言差异、段落节奏和自然省略；避免概述代替戏、重复解释、套话、平均句长、
机械三段式和无代价情绪。它是 Agent 层的写作契约，不是一个可被随意调用或绕过的
`draft_prose` 工具。

场景节拍保留为规划单位，用来说明每个阶段的目标、阻力、行动、信息和状态变化。
正文仍按完整章节提交；不存在场景正文版本、场景组装或硬审核链。作者手工修改和
Style Auditor 的局部建议都形成普通章节版本，后续写作只认最新 HEAD。

## 6. 对话与上下文

近期对话直接进入模型；较早对话通过稳定的 `book/notes/conversation-history/` 逐条资源和 `grep/search`
按需检索。系统不能只截断最近若干轮后假装拥有完整记忆，也不能把所有历史永久塞入
每次请求。

作品内部搜索优先使用 SQLite FTS5、结构化索引、标题/实体别名扩展和中文稀疏排序。
这套方案在 1 GB VM 上可运行，并且结果可解释。向量检索不作为当前正确性的前提；
未来只有在真实长书评测证明稀疏召回不足时，再增加可选的外部向量后端或离线小型索引。

## 7. 拆书与参考文风：当前实现

拆书不是单独的报告展示器，而是“带来源证据的阅读层”。分析内容和正文共享同一个
作品身份与内容版本键，但不共享可编辑 main 历史：正文与 Tag 决定分析对象，分析有
自己的生成、失效、人工采用和删除生命周期。

### 7.1 导入和章节切分

1. 保存原始上传文件、SHA-256、编码、换行信息和规范化文本；原始文件永不被分析结果
   覆盖。
2. 先用确定性规则找候选边界：章节标题、卷标题、空行密度、序号模式和段落长度。
3. 对没有可靠标题的文本使用保守的长度与段落边界评分；低置信边界在导入预览中允许
   作者合并、拆分和改名。
4. 每章保存原文起止 offset、规范化内容哈希、标题来源和边界置信度，保证分析证据能
   回跳原文。
5. 切分规则升级不会静默重切已有作品；重新切分会创建新的导入版本。

### 7.2 分层分析

每章分析拆成可独立重试的层，而不是一次生成一个巨型 JSON：

- 结构层：字符、段落、句子、句长分布、段长、对话比例和首尾片段，由程序确定性计算；
- 事实层：人物、场景、事件和伏笔，只记录正文明确支持的内容；
- 叙事层：场景职责、冲突、关系变化、信息释放、节奏和结尾钩子；
- 文风层：视角、叙事距离、句段节奏、对话、描写、信息流、情绪、用词、修辞、转场
  和场景出入；
- 技法层：局部手法、作用、适用条件、失效条件、执行规则和原创性边界；
- 全书聚合：人物出场、事件时间线、伏笔生命周期、节奏分布和跨章文风画像。

结构层由程序计算。其余章节层的每个判断必须引用冻结章节中的字符范围，服务端会用
`source[start:end] == quote` 逐字回查。全书聚合只消费已经验证的章节层和真实章节
位置，不能把自由生成的总结升级为原文事实。

文风层和技法层都不能保存“像某位作者”这种不可执行标签。文风层描述反复出现的叙述
机制，技法层描述局部方法；二者都必须给出不依赖原作内容的执行规则和明确的原创性
边界。全书文风画像不携带证据引文，只保留定量指标、主导标签、章节覆盖率、规则和
边界；需要核实时再回到章节层证据。

### 7.3 失效与复用

分析键包含章节身份、`content_hash + analyzer_schema_version + layer + provider + model`。
创建 Tag 时，如果章节内容哈希和分析 schema 相同，可以复用已有分析；
内容变化只失效受影响章节及依赖它的跨章聚合。模型或提示升级可以并存新旧分析，不
覆盖旧结果。

参考书分析只生成证据化观察和技法候选。作者采用时复制的是抽象后的执行规则、适用
范围和原创性边界，不复制参考书人物、专名、独特措辞或具体情节。创作作品的分析则可
继续进入 Story Memory 与连续性重放。

### 7.4 当前已完成的切片

1. 导入预览显示候选章节、offset、字数和边界置信度，支持改名、合并和按光标拆分；
2. 五个章节层独立保存和重试，模型结论可以点击回到原文证据；
3. 内容哈希与 schema 版本共同控制分析缓存；
4. 全书聚合人物、事件、伏笔、节奏和文风画像；
5. 技法结论可以保存为待作者绑定的技法卡；
6. 参考书对话和来源相连的创作项目可以按需读取
   `book/analysis/reference/style-profile.json`。

### 7.5 下一次真实小说验收

用户提供参考小说后，测试不能只确认任务状态为 completed：

1. 先确认导入边界，记录人工合并、拆分和改名次数；
2. 完成全书分析后，从开头、中段、转折和结尾分层抽样，逐条核对证据与事实；
3. 检查同一文风维度的标签是否在章节间漂移，并观察画像覆盖率是否与阅读判断一致；
4. 选择少量高覆盖规则，明确要求 Agent 参考这些抽象机制生成原创章节；
5. 对比未使用画像的基线，记录盲评、连续性错误、作者修改量、成本和延迟；
6. 若生成复用了原作独特措辞、意象、专名、物件或情节，视为失败，不以“风格更像”
   抵消原创性问题。

## 8. 可靠性与资源上限

- SQLite 只由一个应用进程写入；低内存部署保持一个 Uvicorn worker 和一个 AI 并发。
- 生成任务持久化，服务重启后只恢复安全状态的任务；模型请求必须有超时与可取消标记。
- edit buffer 设置单章、单用户总量和保留期；启动时清理过期暂存。
- 历史、对话、搜索和分析列表必须分页；首屏不得加载全书全部版本或全部分析正文。
- 完整备份必须包含数据库、不可变正文、Tag、导入原文与分析文件，并在恢复前后校验
  清单和哈希。
- 清理永远以数据库引用和当前数据库拥有的项目根为边界，不跨实例扫描或删除。

## 9. 验收条件

每次架构修改至少验证：

1. 全量单元与 Web 测试；
2. `ruff`、Python 编译和数据库迁移；
3. `readraft-doctor` 零错误；
4. 新建作品、导入、创建 main、写一章、局部修改、撤回、恢复、打 Tag、读取 Tag；
5. 服务重启后任务、暂存和最近阅读位置仍正确；
6. 使用真实 Provider 完成一次流式对话、工具读取、正文 compose 与 HEAD 推进；
7. 不打印 API Key、模型私有推理或正文内容到诊断输出。

当前实现已经满足前四项的自动化覆盖；真实 Provider 验收应在具有稳定凭据加密密钥的
部署环境执行。本地复制的加密凭据不能用另一套密钥解密，也不应通过猜测或回显绕过。
