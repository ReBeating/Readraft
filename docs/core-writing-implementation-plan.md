# 长篇小说创作核心：技术实现计划

> 关联文档：[产品定义、当前状态与实现路线](product-definition-and-roadmap.md)
>
> 更新日期：2026-07-24
>
> 目标：在现有 FastAPI + SQLite MVP 上实现真正的“创作闭环 MVP”

## 1. 决策摘要

接下来应暂停扩充普通编辑器和独立拆书页面，把开发重心集中到以下主链：

```text
作品定位
→ 作者确认的全书蓝图与规划剧情线
→ 分卷和动态章节大纲
→ 章节任务卡与场景节拍
→ 上下文编译
→ 逐场景生成、版本化与 Scene Auditor
→ 安全组装章节候选版本
→ 整章硬性一致性检查
→ AI 味审校与定点修改
→ 作者确认正文
→ 提取并确认 Story Delta
→ 更新正史 Memory
→ 滚动调整未来细纲
```

第一阶段只支持一本小说的主线分支，但数据模型预留 `branch_id`。不在第一阶段实现多人协作、自动发布、向量数据库、Neo4j、多个常驻 Agent 或整本书一键生成。

## 2. 开头讨论确定的原始需求

最初需求不应被缩减为“调用 DeepSeek 写一章”。完整需求包括：

1. 使用个人 DeepSeek API Key；
2. 在低配置 Azure Linux VM 上轻量运行；
3. 持久化而且可校验的小说 Memory；
4. 设计人物、世界观、总纲和卷纲；
5. 维护未来 10–30 章的滚动细纲；
6. 每章正文至少 2000 个有效字符；
7. 推荐目标为约 2600–3200 字，可由项目调整；
8. 生成新章节、续写和调整已有章节；
9. 旧章节修改必须创建版本，不能直接破坏正史；
10. 区分客观事实、角色知情、作者计划和读者已知信息；
11. 追踪人物状态、关系、位置、物品、时间线、伏笔和剧情承诺；
12. 根据读者意见提出多个剧情调整方案，由作者决定；
13. 读者意见不能直接污染正史或控制正文；
14. 写后进行一致性、节奏、文风和 AI 味检查；
15. 作者确认后，正文和 Memory 变化才成为正史；
16. 拆书结果应转化为抽象技法并回流创作；
17. 保留人工控制、版本恢复和修改影响检查。

## 3. 开头调研方法的组合方式

我们之前并没有决定照搬某一个项目，而是组合以下思想：

| 来源 | 借鉴内容 | 在本项目中的实现 |
|---|---|---|
| InkOS | 不可变状态更新、时序 Memory、写作—审计—修订 | 候选版本、Story Delta、正史提交 |
| 天命 | 事实快照、变更声明、生成门禁 | 结构化事实、硬检查、作者确认 |
| DOME | 动态分层大纲、时间知识、相关事实检索 | 滚动细纲、时间线、Context Compiler |
| novel-creator-skill | 写前准备、Beat Sheet、写后更新和压缩 | 章节任务卡、上下文构建、写后流程 |
| oh-story | 中文网文节奏、爽点、钩子、去 AI 味 | 网文章节卡、软质量检查、声纹审校 |

核心原则仍是：

> **数据库负责事实，LLM 负责提案和文本，作者决定什么成为正史。**

## 4. 现有 MVP 如何处理

### 4.1 保留

- FastAPI 单进程服务；
- SQLite WAL；
- Jinja 页面和少量原生 JavaScript；
- 用户登录、会话、CSRF 和个人 API Key；
- DeepSeek 调用、超时、重试和 token 记录；
- 单任务后台队列和进程锁；
- 现有小说项目、人物卡、章节和文件存储；
- TXT 导出；
- 拆书上传、切章和逐章结构化分析。

### 4.2 增强

- `novel_projects`：加入作品承诺、目标读者、核心爽点、结局约束和滚动规划窗口；
- `novel_story_blueprint_versions` / `novel_story_blueprint_heads`：保存不可变全书蓝图修订，以及当前版和确认版指针；
- `novel_plot_arcs` / `novel_plot_arc_versions`：保存长期规划线身份、不可变修订，以及当前版和确认版指针；
- `novel_chapters`：加入卷、滚动结构骨架、章节任务卡、正史版本和重检状态；
- `novel_chapter_versions`：加入父版本、候选/正史状态、内容哈希和变更来源；
- `novel_scene_versions`：保存逐场景生成、手工编辑和恢复产生的不可变正文版本；
- `scene_quality_audits` 与 `novel_scene_assembly_items`：保存场景审校结果和章节组装所用的精确版本来源；
- `generation_jobs`：扩展为多种写作阶段任务，并保存实际上下文快照；
- `writing.py`：从一次性 Prompt 变成 Context Compiler + 多阶段任务。

### 4.3 逐步拆分

当前 `main.py`、`db.py` 和 `worker.py` 已经过于集中。后续按职责新增模块，不做一次性重写：

  planning_ai.py       章节任务卡 Planner

## 5. 目标领域模型

### 5.1 作品与动态大纲

#### `novel_projects`

保留现有字段，增加：

- `story_promise`：作品向读者提供的核心体验；
- `target_audience`；
- `core_appeal`：主要爽点或情绪价值；
- `ending_constraint`：不能轻易破坏的终局承诺；
- `planning_horizon`：滚动细纲章数，默认 20；
- `canonical_branch_id`；
- `workflow_version`。

#### `novel_volumes`

- `id`
- `project_id`
- `position`
- `title`
- `goal`
- `start_state`
- `end_state`
- `major_conflict`
- `payoff`
- `status`

#### `novel_story_blueprint_versions` 与 `novel_story_blueprint_heads`

- 每次保存或恢复都创建不可变蓝图版本；
- 蓝图记录核心悬问、主角长期目标、冲突引擎、长期代价、开篇/终局状态、关键转折、必须兑现项、禁止捷径和作者备注；
- Head 分开记录 `current_version_id` 与 `confirmed_version_id`；
- 草稿可以不完整，但不会进入任何模型上下文；
- 确认版满足结构校验后才进入 Planner、Writer、审校器与 Reader Planner；
- 恢复历史版本只创建新的草稿，不移动确认指针；
- 后续确认新的蓝图版本会把未来已确认任务卡退回草稿并标记章节待复查，已有正史不被改写。

#### `novel_plot_arcs` 与 `novel_plot_arc_versions`

- `novel_plot_arcs` 保存稳定剧情线身份；版本表保存不可变内容；
- 类型支持主线、支线、人物弧光、关系线、谜团线和世界线；
- 记录悬问、对读者的承诺、起始状态、目标回报、涉及人物、计划转折、优先级、作者备注和计划生命周期；
- Arc Head 分开记录当前版与确认版；草稿修订不会覆盖旧确认版；
- 放弃剧情线通过创建已确认的 `abandoned` 版本实现，不做硬删除；
- 确认版变化或放弃时，只让未来任务卡中引用旧/新精确标题的章节待复查。

这里的“规划剧情线”是写前计划，不是正史投影。正史中的剧情线状态仍来自作者确认的 Story Delta，二者不能互相回填或混为一张表。迁移也不会把历史 `plot_threads` 猜成作者的全书计划。

#### 确定性全书结构体检

`structure_health.py` 不增加一套与章节骨架竞争的状态，也不保存模型结论。
它每次从当前权威数据实时计算报告：

- 以最高正史章为边界，扫描其后的全部未来章节，而不是只看首页的
  `planning_horizon`；
- 检查章节位置连续性、分卷位置单调性、卷归属、结构职责、章节目的、
  2–5 个关键推进点、精确确认剧情线和章末推动；
- 检查同职责长连续段、连续缺少反转/兑现、未来卷缺少阶段反转或回报、
  推进中主线的长空窗；
- 使用 `skeleton_application_id` 与结构应用记录还原每章来源；作者逐章
  修订会清除该来源 ID，明确显示为“作者接管”；
- 只在正史进入未来，或相邻未来章节来源变化时建立接缝。来源变化本身
  不产生问题；同卷无共享剧情线、同卷重新建立、跨卷前未收束时才提示；
- 每项结论都携带原字段证据和章节、分卷或剧情线编辑链接。

这份报告只区分可以确定举证的“硬缺口”、需要作者判断的“待核对”和低优先级
“观察项”。它不调用 DeepSeek，不判断两个情节在语义上是否精彩或自然，
也不自动改纲。第一版不需要数据库迁移，低配置 Azure 主机只承担几次有界
SQLite 查询和线性扫描。

#### `novel_chapter_causal_links`

- 作者显式记录较早章的 `cause_text` 与较晚未来章的 `effect_text`；
- 关系类型为 `causes / enables / complicates / pays_off`；
- 服务端强制起因章位置小于结果章，且结果章必须在当前正史边界之后，
  因此不需要概率式环检测也能保证规划图无环；
- 链接可以跨确认剧情线与滚动结构来源；跨窗口链接可作为接缝的明确证据；
- active 链接只进入起因章和结果章的 Planner / Writer / Scene Writer
  上下文，且明确标记为未来约束而非正史；
- 建立或归档链接会使相关未来任务卡退回草稿、场景稿按现有规则过期，
  但不会修改正文、候选版本或正史；
- 结果章成为正史后，链接不再进入生成上下文，实际 Story Delta 和
  `story_events.cause_event_keys` 接管已发生因果。

#### `novel_causal_link_suggestions` 与审阅记录

- 作者指定未来 2–80 章后，服务冻结确认蓝图、剧情线、正史 Memory/事件、
  未来骨架、确认任务卡和已有因果链接；
- DeepSeek 只返回 0–8 条候选，每条引用快照内的精确章节 ID，并提供起因/
  结果证据、桥接目的、遗漏风险和置信度；零候选必须说明原因；
- 同一结果存在两项以上可信前因时，结果用稳定的零基候选索引建立 2–4 项
  比较组；每项记录名称、反证或证据缺口、可推翻条件和中间步骤就绪状态，
  组级记录这些解释互斥、可并存或现有证据无法判断；
- 服务从项目、确认蓝图/剧情线、正史 Memory、人物知情、当前状态、
  连续性问题与章节骨架构建稳定证据目录；新版每条候选必须恰好完成
  正史事实、人物知情、时间先后、世界规则与连续性五类检查，并且只能引用
  目录中逐字存在的证据 ID；
- 五类检查只允许 `supported`、`uncertain`、`conflict`。它们表示模型对
  当前冻结证据的预检，不是自动真值；冲突必须说明待解决项；
- 每条候选必须按精确确认剧情线 ID 推演所涉及剧情线的变化前后、影响类型、
  风险和可选的中间承接章节；服务端校验剧情线标题与章节区间，跨线候选不能
  漏掉任一端涉及的确认剧情线；
- 候选保存在独立持久队列，不会进入 Planner、Writer 或正史上下文；
- 作者可以逐条编辑起因/结果后确认，或只保存忽略决定；采纳调用正式因果
  链接服务并在同一事务保存审阅记录；比较组必须先确认已核对其他解释，
  缺中间步骤时必须在作者判断中说明补写或直接采用的理由；新版候选必须
  确认已核对语义与跨线影响，存在冲突时还必须记录作者覆盖理由；
- 采纳时重新核对完整结构基线。来自同一批已采纳候选的链接会从比较基线中
  排除，使作者可继续审阅同批其他候选；其他正史、骨架、确认计划或链接变化
  都会阻止旧候选；
- 这层只提供有界语义建议，不声称自动证明自然语言因果，也不自行连线。

#### `novel_causal_branch_simulations`

- 只有尚未采纳或忽略、且通过证据引用式语义预检的因果候选可以发起沙盘；
- 每次任务冻结所选候选、未来连续 10–30 章、确认蓝图/剧情线、人物、正史、
  连续性账本、现有链接与稳定证据目录，并保存候选签名和完整基线指纹；
- 输出必须恰好包含 `minimal_change`、`distributed_consequences`、
  `stress_test` 三种实质不同分支，顺序固定；
- 每种分支至少引用三章且必须包含候选结果章；章节 ID、位置、标题，人物名，
  剧情线 ID/标题，蓝图必须兑现项和全部证据 ID 都由服务端逐项核对；
- 每种分支分别保存逐章变化、因果角色、证据状态、剧情线轨迹、人物知情渠道、
  回报时机、取舍、失效条件与总体风险。存在人物或蓝图必须兑现项时，不允许
  用空列表绕过相应检查；
- 任务使用独立持久队列、租约恢复、个人 DeepSeek 凭据和每日额度；服务重启
  后安全重排。结果生成后即使基线改变或原候选后来被决定，也保留为历史快照；
- 沙盘页面不能直接修改规划。只有作者先通过原候选的全部决策门并建立正式
  因果链接后，才可把其中一条分支转成独立的逐章落地清单。

#### `novel_causal_branch_adoptions`

- 每份清单绑定一条已完成沙盘、一个分支和一条作者确认且仍 active 的原因果
  链接；创建清单只冻结相关未来章节与任务卡，不修改规划；
- `novel_causal_branch_adoption_items` 按分支中的逐章影响保存不可变来源、
  可编辑任务卡补丁和 `pending / accepted / rejected` 作者决定；
- 补丁只允许增加“必须落实”、推演已引用的确认剧情线、伏笔铺设与回收，
  不改标题、正文、正史、候选版本或原因果链接；
- 所有条目必须逐项决定，至少采用一项。最终应用重新校验未来正史边界、
  来源链接、相关章节精确基线和运行中任务，并在单一事务中只写已采用项；
- 应用同步更新未来骨架关键事件与任务卡草稿，使已有场景稿按计划变化规则
  过期；保存应用前后状态。若应用后未继续编辑，可安全撤销且不会归档链接。

#### `novel_chapter_plans`

每章独立任务卡：

- 本章存在的理由；
- 开始状态与结束状态；
- 主要冲突；
- 情绪价值或爽点；
- 必须推进的剧情线；
- 必须保留与禁止发生的事实；
- 伏笔埋设或回收；
- 章末钩子；
- 目标字数；
- 计划状态和作者确认状态。

#### `novel_scene_beats`

一章包含 2–5 个可排序场景节拍：

- 视角人物；
- 场景目标；
- 阻力；
- 行动与策略；
- 信息揭示或隐藏；
- 潜台词；
- 地点与关键物件；
- 场景结束状态；
- 对下一场景的推动；
- `requirement_refs_json`：逐字引用本任务卡中的推进线、必须发生、伏笔铺设/
  回收和章末钩子，明确每个场景实际负责什么。

系统同时提供一次生成 2000–4000 字整章正文的快速路径和更可控的逐场景路径。逐场景 Writer 只负责当前节拍，读取前一场景正文和相邻节拍边界；全部场景通过组装前检查后，才按任务卡顺序形成新的章节候选稿。

作者已保存的任务卡还可进入“只拆场景”模式。服务冻结完整任务卡指纹，
DeepSeek 只能返回场景字段，不能重写章节级约束；每条推进线、必做事件、伏笔
和钩子都必须逐字映射到至少一个场景。结果只替换场景并把任务卡保持为草稿，
作者可编辑映射后再确认。落库前任务卡或既有场景发生变化时，旧结果被拒绝。

#### `novel_scene_versions`

- 每次生成、重写、手工保存和恢复都创建不可变版本；
- `plan_fingerprint` 记录版本对应的场景计划；
- 任务卡修改时复用同位置场景 ID；计划内容变化会把现有正文标记为过期；
- 被移除的场景改为 `retired`，不级联删除历史版本和既有组装来源。

#### `scene_quality_audits` 与 `novel_scene_assembly_items`

- Scene Auditor 针对一个精确场景版本保存结构化结论；
- 未通过或待审场景只有在作者填写覆盖原因后才能参与组装；
- 组装记录每个位置使用的 `scene_beat_id` 与 `scene_version_id`；
- 组装只创建 `scene_assembly` 章节候选版本，不修改 `canonical_version_id`。

### 5.2 章节版本与正史

#### `novel_chapter_versions`

在现有表上增加：

- `parent_version_id`
- `status`：`candidate / canonical / archived`
- `source`：`manual / generated / targeted_rewrite / restored`
- `content_hash`
- `change_summary`
- `created_by`

#### `novel_chapters.canonical_version_id`

章节当前正文与正史必须分开：

- 编辑器可以保存工作版本；
- AI 只能创建候选版本；
- 只有作者点击“接受为正史”后才更新 `canonical_version_id`；
- 更新旧章正史时，后续章节被标记为 `needs_recheck`；
- 旧版本永远保留并可恢复。

### 5.3 结构化 Story Memory

Memory 不是聊天记录，也不是单纯摘要。

#### `story_entities`

统一记录：

- 人物；
- 地点；
- 势力；
- 物品；
- 能力；
- 世界规则；
- 重要概念。

每个实体有稳定 ID，改名不改变 ID。

#### `story_facts`

每条事实至少保存：

- `project_id`
- `branch_id`
- 主体、关系、客体或结构化值；
- 生效和失效范围；
- 来源章节版本；
- `proposed / canon / retracted` 状态；
- 置信度；
- 是否经过作者确认。

#### `character_knowledge`

单独记录人物对事实的认知：

- 知道；
- 怀疑；
- 误以为；
- 不知道；
- 从何时、通过何事获得；
- 来源版本。

这样可以阻止人物突然全知或提前泄露秘密。

#### `story_events`

- 稳定的 `event_key`；
- 事件摘要；
- 参与实体；
- 地点；
- 故事内时间；
- 自然语言原因和指向此前事件键的 `cause_event_keys`；
- 来源版本。

#### `memory_identities` / `memory_identity_aliases`

- 按作品隔离人物、地点、物品、事实、剧情线、伏笔和事件身份；
- 保存标准称呼、保守规范化键与作者确认的别名；
- 身份规则变化时迁移投影引用，并在同一事务中重放当前正史；
- 不自动猜测两个自然语言表述是否同义，避免错误合并污染正史。

#### `foreshadowing`

- 埋设内容；
- 当前状态；
- 来源章节；
- 预期回收范围；
- 实际回收章节；
- 是否废弃。

#### `chapter_memory`

每个正史版本保存：

- 章节摘要；
- 场景摘要；
- 关键词；
- 关键事件；
- 涉及实体；
- 未解决问题。

#### `story_deltas`

LLM 对一章提出结构化变化：

```json
{
  "chapter_summary": "",
  "character_changes": [],
  "relationship_changes": [],
  "location_changes": [],
  "item_changes": [],
  "knowledge_changes": [
    {
      "character_name": "",
      "fact": "",
      "canonical_fact": "",
      "state": "knows"
    }
  ],
  "plot_thread_changes": [],
  "foreshadowing_changes": [],
  "events": [
    {
      "event_key": "",
      "summary": "",
      "cause_event_keys": []
    }
  ],
  "time_advance": null
}
```

Story Delta 的状态为：

```text
proposed → author_edited → accepted → projected
                         ↘ rejected
```

只有 `accepted` 的 Delta 才能更新正史事实表。

## 6. Context Compiler

生成质量和长篇连续性的核心不是扩大 Prompt，而是确定性地选择正确上下文。

### 6.1 输入分层

```text
固定层
  作品承诺、世界规则、视角、作品声纹

计划层
  确认版全书蓝图
  Planner：全部确认且未放弃的规划剧情线
  Writer / Auditor：本章任务卡精确选中的确认版规划剧情线
  卷目标、本章任务卡、场景节拍、读者需求的已采纳方案

事实层
  出场人物当前状态和知情边界
  本章涉及的地点、物件、剧情线和伏笔

近因层
  最近章节摘要、前一章正文末尾、当前工作版本

任务层
  本次生成或修改的明确要求、禁止事项和输出格式
```

### 6.2 检索顺序

第一阶段不使用向量数据库：

1. 根据章节计划中明确绑定的实体 ID 查找；
2. 根据剧情线和伏笔 ID 查找；
3. 读取最近 3–5 章摘要；
4. 用 SQLite FTS5 对摘要和事实做关键词补充检索；
5. 在字符预算内按相关性和时间排序；
6. 将最终上下文保存到任务快照，保证结果可以复现和审计。

FTS5 补充检索现已实现：

- `story_memory_search_documents` 作为带项目和章节外键的正史搜索文档表；
- `story_memory_fts` 使用 `unicode61` 和中文二/三元词扩展索引章节摘要、事件、事实、人物知情、剧情线和伏笔；
- Story Delta 投影、旧正史撤回和项目删除会在同一事务中同步搜索索引；
- 查询由当前场景、任务卡、章节信息和本次作者要求确定，只允许命中本作品、当前正史分支、当前章之前的记录；
- 最近 5 章继续走确定性固定上下文，不在检索结果中重复；
- 查询概念会按作者确认的身份别名双向扩展，但不会用模型临时猜测同义词；
- 人类可读概念、完整内部检索词、命中来源和排序结果均写入任务快照，并在任务页展示。

确定性状态回放现已实现：

- `continuity_replay_runs` 记录每次 Delta 投影、正史切换或迁移触发的完整回放；
- `story_state_snapshots` 保存每个正史章节结束后的累积状态，不依赖模型临时总结；
- `story_state_snapshots` 同时保存人物知情边界、剧情线/承诺和伏笔生命周期的当前状态；
- `continuity_issues` 使用稳定指纹记录人物、关系、地点、物品持有者、故事时间和生命周期的冲突；
- 人物知情支持 `knows`、`suspects`、`believes_false`、`forgets`；无此前知情基线的遗忘会产生待核对项；
- 剧情线支持开启、推进、暂停、解决、放弃，伏笔支持设置、推进、回收、放弃；已关闭对象再次推进会产生硬冲突；
- 人物、事实等状态先解析到作者确认的标准身份；身份规则保存或移除后会迁移引用并重放当前正史；
- 事件使用稳定 `event_key`，只为引用此前已发生事件的 `cause_event_keys` 建立直接因果边；缺失前因产生待核对项，自引用或事件身份冲突产生硬冲突；
- 回放只读取当前作品、当前正史分支、当前正史版本且状态为 `projected` 的 Delta，并严格按章节位置执行；
- 旧正史撤回和新 Delta 投影在同一数据库事务内完成回放，不会出现记忆已变而状态仍旧的中间状态；
- Context Compiler 只读取当前章之前的最新快照与仍有效问题，并在总字符预算内优先保留相关实体；
- 作者可以记录“有意保留”的判断，但确认不会删除问题、伪造状态或绕过正文 Hard Auditor。

向量检索只能在后续作为补充，不能决定什么是正史。

## 7. 一章的完整工作流

当前代码已经增加确定性的章节执行状态机。它不替作者自动跨过任何门禁，
而是根据当前任务卡、场景就绪数、工作版本、硬审计、声纹审校、正史指针和
Story Delta 状态，统一推导六步进度与下一项安全操作：

```text
确认任务卡
→ 形成正文候选（逐场景或整章）
→ 通过硬审计
→ 去 AI 味审校（软门禁，可明确跳过）
→ 作者确认正史
→ 审核故事记忆
```

作品工作台会定位第一章尚未闭环的章节；章节、任务卡、场景、硬审计和
AI 味页面复用同一状态结果。正史记忆自动提取失败、缺失或被拒绝时，
作者可以从当前正史版本重新发起 Observer，结果仍只会停在待审核提案。

### 7.1 Planner

输入确认版全书蓝图、全部确认且未放弃的规划剧情线、滚动大纲、正史状态和作者要求，输出结构化章节任务卡与 2–5 个场景节拍。任务卡中的 `plot_threads` 应优先使用规划剧情线的精确标题，并只选择本章实际推进的线。所有可确认任务卡都必须显式建立任务要求到场景的完整覆盖关系。

作者可以编辑后确认。未经确认的计划不能自动开始正文生成。

若章节级任务卡已经由作者写好，或由长期分支落地清单更新，作者可改用
Scene Planner：冻结当前任务卡，只生成场景节拍。模型输出、服务端校验和
最终落库都不能改动任务卡的章节级字段；基线变化时任务失败而不是覆盖。

### 7.2 Writer

Writer 支持两种明确模式：

- 整章模式：根据完整任务卡一次生成整章候选正文；
- 场景模式：只生成或重写当前场景，不代写下一场景，并带入当前节拍、相邻节拍边界、前一场景正文和精确作用于该场景的技法。

整章模式的字数规则：

- 项目可设置目标；
- 默认目标 2600–3200 个有效字符；
- 硬下限 2000；
- 忽略空白后计数；
- 不足时只允许一次“补齐缺失节拍”的定向扩写；
- 第二次仍不足则保留候选，但标记为不合格，不能自动成为正史；
- 禁止通过重复总结、无效环境描写或同义改写灌水。

场景目标字数由章节目标和场景数量确定；每个生成结果都先创建独立场景版本，再接受 Scene Auditor 检查。

### 7.3 Scene Auditor 与安全组装

Scene Auditor 只审查当前场景的职责：

- 与正史事实、人物知情和世界规则是否冲突；
- 是否完成当前节拍的目标、行动、揭示、隐藏和结束状态；
- 是否越过前后场景边界，提前完成下一节拍；
- 视角是否越界；
- 是否达到按章节目标分配的场景有效字符下限。

手工保存或恢复的版本进入待审状态；生成版本在同一后台任务中自动审校。任务卡变化后，计划指纹不再匹配的场景会变成过期状态，不能组装。只有所有活动场景均为 `pass` 或记录了作者覆盖原因时，系统才按位置组装，并保存精确的场景版本来源。

### 7.4 Hard Auditor

硬性检查可以阻止正史提交：

- 与已确认事实冲突；
- 人物使用了自己不知道的信息；
- 违反世界规则；
- 漏掉任务卡中的必须事件；
- 出现明确禁止事项；
- 视角越界；
- 字数不足；
- 关键人物、地点或物件状态矛盾。

场景组装稿仍是候选版本，必须继续通过本节的整章检查；Scene Auditor 不能替代 Hard Auditor。

### 7.5 Style / AI 味审校

软质量检查不直接重写全文，只产生可定位问题：

- 原文位置和原句；
- 问题类型；
- 判断证据；
- 严重程度；
- 对阅读体验的影响；
- 建议修改方向。

作者选择某个问题后，系统仅重写目标段落，并提供 1–2 个候选版本和差异对照。

### 7.6 作者确认

作者可以：

- 继续手动修改；
- 接受某个候选版本；
- 忽略软问题；
- 退回重新规划；
- 将当前版本接受为正史。

硬问题必须解决或由作者明确覆盖，并记录覆盖原因。

### 7.7 Observer

正文确认后，Observer 提取 Story Delta。作者审核和修改 Delta 后再提交 Memory。

不能从未确认的 AI 草稿更新事实，否则错误会污染后续章节。

## 8. 修改旧章节

修改旧章的流程：

```text
选择正史版本
→ 创建新候选版本
→ 修改正文
→ 对比差异
→ 重新执行硬检查
→ 提取新 Story Delta
→ 计算旧 Delta 与新 Delta 的差异
→ 列出受影响的后续事实、伏笔和章节
→ 作者确认
→ 切换正史版本
→ 从最近检查点重放后续 Delta
```

第一阶段可以先实现“标记后续章节需要重检”，第二阶段再做完整自动重放和分支比较。

## 9. 读者意见调整剧情

读者意见保存为结构化 `reader_requests`，不能直接进入 Writer Prompt：

- 原始意见；
- 类型；
- 影响范围；
- 硬性或软性优先级；
- 不可破坏的约束；
- 作者备注；
- 状态。

Planner 针对一条请求生成三个方案：

```text
方案摘要
满足了什么
牺牲了什么
影响哪些人物、剧情线和承诺
需要修改哪些未来章节
是否影响已发布正史
风险
```

只有作者采纳的方案才会更新未来滚动细纲。已经发表的事实默认不可改。

## 10. 去 AI 味的数据模型

#### `novel_voice_profiles`

- 声纹特征；
- 禁用表达；
- 对话规则；
- 句式和段落节奏；
- 描写比例；
- 作者备注；
- 状态：草稿或已确认；只有已确认状态可进入 Writer、Scene Writer 和 Style Auditor。

#### `voice_profile_suggestions`

- 作者拥有权利的样章标题、正文、哈希和字符数；
- 作者补充的创作意图；
- 模型提出的叙述、节奏、对话、感官、比喻和留白规则；
- 每条观察对应的样章原句证据，以及有效/丢弃证据数；
- 模型、凭据来源、token、错误、原始响应与最终应用快照；
- 队列状态：排队、运行、待审核、已应用、已放弃或失败；
- claim token 与租约，服务重启或任务失联后可安全重新排队。

模型只能提交建议。服务端会逐字确认每段证据确实存在于样章中，且至少保留两段有效证据；否则任务失败且不会修改 `novel_voice_profiles`。作者可逐项改写建议，并明确选择保存草稿或确认应用。未确认声纹不会进入写作上下文。

#### `style_reviews`

- 目标版本；
- 审校状态；
- 综合观察；
- 问题数量；
- 使用的声纹版本。

#### `style_issues`

- 原文引用和内容哈希；
- 段落位置；
- 问题类别；
- 理由和影响；
- 严重程度；
- 状态：待处理、已接受修改、忽略、误报。

#### `author_style_preferences`

记录作者在定点 AI 味审校中接受或忽略了什么建议，继续作为 Style Auditor 的基础反馈。

#### `editing_preference_suggestions`

- 来源限定为作者手工保存且具有父版本的章节或场景版本；
- 保存来源版本 ID、内容哈希、有界差异、实际变化字符数和作者的改稿说明；
- 保存模型、凭据来源、token、原始响应、有效/丢弃证据数和失败原因；
- 队列状态为排队、运行、待审核、已应用、已放弃或失败，并使用 claim token 与租约支持崩溃恢复；
- 不直接修改声纹或启用偏好。

模型只能从有界差异中提出候选。服务端重新读取两个不可变版本、核对内容哈希，并逐字定位修改前/后证据；双侧证据还必须位于同一个差异块。找不到证据的候选会被丢弃，没有有效候选时任务失败且不产生偏好。

#### `author_editing_preferences`

- 类别；
- 作者确认或改写后的抽象 `guidance`；
- 规则的 `applicability`；
- 用于审计的修改前/后证据；
- 启用或归档状态；
- 来源建议与时间。

作者必须逐项确认候选。Writer、Scene Writer、Style Auditor 和上下文快照只读取启用记录的 ID、类别、抽象规则、适用范围和更新时间，不读取证据原文；归档后立即退出上下文。偏好不自动修改作品声纹。

#### `author_editing_preference_aggregates`

- 同类别的稳定抽象规则、适用范围与不进入 Writer 的作者说明；
- 启用、停用、确认和归档时间；
- 只有作者确认后生效。

#### `author_editing_preference_aggregate_evidence`

- 把原始确认规则标记为 `support` 或 `conflict`；
- 至少需要来自两次不同手工改稿的支持项；同一次改稿的多个候选不能凑数；
- 启用聚合时，关联的支持与冲突源规则从生成上下文中逻辑折叠但不删除；
- 停用聚合后，仍启用的源规则恢复进入上下文，历史关系继续保留。

编辑记忆页只用同类别和透明的文字重合提示帮助作者整理，不自动作语义合并。确认前后的审校反馈按内容哈希去重、使用相同审校器，并要求两侧各至少 3 版、3 章与 6000 有效字；它的名称是“相关问题观察率”，不作为规则效果或因果证明。

## 11. 拆书如何接入创作

拆书使用独立的参考技法库，不与正史 Memory 混合。第一阶段回流已经实现，Writer 默认看不到参考原文。

### 11.1 已实现的数据模型

`reference_technique_cards` 保存：

- 技法名称和维度；
- 来源文档、章节、分析与证据位置；
- 参考观察及其作用；
- 适用与不适用场景；
- 可执行的抽象规则；
- 必填的原创性边界；
- 作者备注和启用/归档状态。

`novel_technique_bindings` 保存：

- 所属小说；
- 全书、分卷、章节或场景范围；
- 是否用于 `plan / write / audit`；
- 针对当前作品的作者改造；
- 优先级和启用状态。

同一卡片作用于同一章节时，Context Compiler 按范围具体度和优先级去重。归档卡片会停用其全部绑定。

### 11.2 已实现的安全上下文

逐章拆书分析可以提出最多 6 张技法建议。作者必须先保存、检查和绑定，技法才可能进入创作。

Planner、Writer 和 Style Auditor 只接收：

```text
技法名称
维度
抽象执行规则
适用 / 不适用条件
作者针对本书的改造
原创性边界
作用范围与优先级
```

来源观察、证据位置、参考原文、原作人物、物件、情节答案和独特措辞不会进入 Writer。每个实际任务仍保存技法上下文快照，便于复现“哪张卡在什么阶段生效”。

### 11.3 后续增强

下一阶段的交互式拆书需要补充：

- 用户或 Agent 的主张、支持证据和反例；
- 事实、推断、效果判断和个人审美的区分；
- 跨章节与全书分层聚合；
- 相似技法合并、矛盾技法提示和强度控制；
- 采用、改造、避免与实际应用效果反馈。

## 13. 数据库迁移策略

当前数据库包含真实账号和 API Key，不能通过删除重建升级。

现已使用：

```text
schema_migrations
```

每次迁移：

1. 创建迁移前 SQLite 备份；
2. 在事务中执行；
3. 记录版本号；
4. 验证外键和完整性；
5. 保留现有表和数据；
6. 部署切换后只运行当前代码路径；
7. 所有迁移都必须在旧数据库副本上测试。

迁移 v8 增加正史搜索文档表、FTS5 外部内容索引和同步触发器，并对既有作者确认 Memory 执行一次安全回填。

迁移 v9 增加回放记录、逐章状态快照和连续性问题表，并按每部作品的当前正史分支回放已有 `projected` Delta。迁移不调用模型，也不读取候选稿。

迁移 v10 将人物知情、剧情线/承诺和伏笔生命周期纳入确定性状态 Schema，并对每部作品的当前正史分支重新回放。它不新增模型调用，不读取候选稿，也不会把旧历史列表与新的权威当前状态重复注入上下文。

迁移 v11 增加记忆身份与别名表，为人物、事实、知情、剧情线、伏笔和事件补充稳定身份引用，并为事件增加 `event_key` 与 `cause_event_keys`。迁移会保守回填现有投影、重建 FTS5、按当前正史重放状态，不调用模型，也不会自动合并含义相近但未经作者确认的文本。

迁移 v12 增加样章声纹建议、证据计数、作者审核结果和可恢复队列租约。它不修改已有作品声纹；既有草稿/确认状态保持不变，只有作者主动应用建议才会更新声纹。

迁移 v13 为场景手工版本增加改稿说明，并增加手工改稿偏好建议队列与作者确认偏好表。它不修改既有 `author_style_preferences` 或作品声纹，也不从历史版本自动生成规则；只有作者主动发起学习并逐项确认后，抽象偏好才会进入后续上下文。

迁移 v14 增加全书蓝图版本/Head，以及规划剧情线身份、版本和当前/确认指针。迁移不调用模型，不从正史 `plot_threads` 或历史剧情线投影自动生成写前计划，也不修改任何既有章节任务卡；旧作品在作者主动建立并确认蓝图前继续以空计划上下文运行。

迁移 v15 增加独立的全书方案任务与采纳记录。任务保存请求时冻结的确认版全书计划、正史、人物知情、未来章节和项目级抽象技法，以及基线指纹、模型原始响应、token、租约和错误；采纳记录保存方案、所选剧情线、实际创建的草稿版本与基线变化标记。迁移不调用模型、不自动生成计划，也不改变任何现有确认指针。

迁移 v16 增加独立的滚动结构建议队列与应用记录，并为未来章节保存结构作用、精确剧情线和章末钩子。应用记录同时保存变更前后状态、精确预览指纹和安全撤销所需信息；迁移不调用模型、不自动创建分卷或章节，也不修改正文、版本、任务卡或正史指针。

迁移 v17 增加作者控制的未来章节因果链接表及查询索引。迁移只创建空表，不从章节大纲或正史事件猜测因果，也不修改已有计划、任务卡、正文或正史；链接必须由作者主动建立。

迁移 v18 增加独立的因果建议队列和逐条作者审阅记录。迁移只创建空表与索引，不启动模型、不回填建议、不创建因果链接，也不修改既有正史、未来规划或任务卡。

迁移 v19 增加独立的长期因果分支沙盘队列、来源候选外键、冻结上下文、候选签名、基线指纹、租约和结果字段。迁移只创建空表与索引，不回填历史候选、不调用模型，也不修改大纲、任务卡、正文、正史或链接。

迁移 v20 增加分支落地清单、逐章审核项、冻结基线、应用前后快照和安全撤销字段。迁移只创建空表与索引，不从历史沙盘自动建立清单，不采纳因果候选，也不修改既有骨架、任务卡、场景、正文、正史或链接。

迁移 v21 为场景节拍增加任务要求引用字段。迁移不猜测旧任务卡与旧场景之间的覆盖关系；缺少显式映射的已确认任务卡会退回草稿，必须由作者或当前 Planner 补全后重新确认。迁移不调用模型，也不修改场景正文、版本、审计或正史。

因果建议统一使用一套严格结果 Schema：对立解释、反证、中间步骤、证据引用式
五类语义预检与精确剧情线联合影响都在同一结果中校验。缺少五类证据检查的历史
结果不再进入审阅或长期沙盘，作者需要按当前冻结上下文重新生成。

## 15. 第一个端到端验收场景

第一轮核心实现完成后，必须通过一条真实的三章流程：

1. 从一句灵感建立作品承诺，让 Story Planner 生成恰好三套完整且实质不同的方案；比较页明确显示结构选择、读者体验、优势、代价、蓝图、剧情线与只读分卷草图；
2. 只采纳其中一套蓝图和一条剧情线；系统创建未确认草稿并保留原确认指针，Planner、Writer 和上下文快照都看不到这些草稿；
3. 补全并确认全书蓝图，建立一条已确认主线和一条未确认支线；Planner 只看到确认线；
4. 让滚动结构 Planner 基于确认计划生成恰好三套 2–6 卷、连续 10–30 章的方案；比较精确的新建、更新与保留清单后采纳一套，随后由作者逐卷、逐章修订；系统只写正史之后的骨架，并让受影响任务卡退回草稿、已有场景稿过期；打开全书结构体检后能看到全部未来职责轨道、剧情线/分卷覆盖和来源记录，作者手改首章后只新增健康的“作者骨架 → 结构窗口”接缝，不把来源变化误报为错误；启动只读因果审查后可得到带双端证据或明确零候选的结果，同一结果存在多项可信前因时显示 2–4 项解释、反证/证据缺口、可推翻条件和缺失中间步骤；每项还显示五类带冻结证据 ID 的语义预检与精确确认剧情线联合影响，未确认时链接表保持不变；从一条待审新版候选发起未来 10–30 章沙盘，必须得到最小改动、分散后果、压力测试三种分支，并逐项显示章节、人物知情、剧情线、蓝图回报、证据与失效条件，生成前后大纲、任务卡、正文和链接表完全不变；作者确认已比较同组解释、核对语义与跨线影响、处理步骤缺口，并在冲突时留下覆盖理由，再编辑并确认一条跨线/跨窗口的“较早章 cause → 较晚章 effect”后，原硬切线由显式桥接解释；此时才选择一个沙盘分支建立落地清单，逐章改写并采用/拒绝，未审完时任务卡不变，最终只更新已采用的未来骨架与任务卡草稿且可在未继续编辑时安全撤销；
5. 确认修改主线后，引用它的未来任务卡退回草稿并标记待复查；只保存蓝图草稿时旧确认版仍继续生效；
6. 从历史蓝图版本恢复时创建新草稿，不覆盖确认版；
7. 粘贴作者自己的样章，提取结果必须展示可在样章中逐字定位的证据；未经作者确认时 Writer 上下文为空，确认后整章与单场景上下文快照都包含该声纹；
8. 第一章任务卡包含 2–5 个场景节拍；
9. 每个场景可独立生成、手工编辑、审校和恢复历史版本；
10. 场景计划变化后旧稿会过期，未全部通过时不能组装；
11. 按任务卡顺序组装不少于 2000 个有效字符的候选正文，且不会自动切换正史；
12. 整章 Hard Auditor 通过后，AI 味审校能够定位具体原文；
13. 对一个问题做定点改写并显示差异；
14. 作者手工保存下一版本后才能发起偏好学习；候选必须展示实际差异中的逐字证据，确认前 Writer 没有新规则，确认后只含抽象规则和适用范围而不含证据，停用后立即移除；
15. 作者接受正文为第一章正史；
16. Observer 提出人物状态、事件、知情变化和伏笔 Delta；
17. 作者修改并确认 Delta；
18. 第二章生成时实际读取第一章确认后的 Memory；
19. 故意让第二章人物知道不该知道的秘密，Auditor 能够拦截；
20. 让第二章遗忘从未获知的事实、继续推进已解决剧情线或已回收伏笔，状态账本能生成对应待核对项或硬冲突；
21. 为同一人物和事实使用两种表述，确认作者归一规则前能看见分裂状态，确认后能合并到一个标准身份并消除伪冲突；
22. 第二章事件通过稳定事件键引用第一章事件，状态账本显示直接因果；替换旧正史移除前因后，系统重新回放并报告缺失引用；
23. 修改第一章正史后，第二、三章被标记为需要重新检查，生命周期和因果状态按剩余正史自动重放；
24. 能恢复第一章旧版本；
25. 服务重启后，全书方案与滚动结构任务/采纳记录、蓝图与剧情线的当前/确认修订、因果建议/逐条审阅记录、长期因果三分支沙盘与未来章节因果链接、声纹建议、手工改稿偏好、正史、章节计划、Memory、身份规则、正史事件因果链和任务状态全部保留；未继续编辑的滚动结构可以安全撤销，已发生后续修改时撤销会被拒绝。
