# 长篇记忆检索架构

## 当前结论

Readraft 暂不引入常驻向量数据库。默认检索链保持为：

1. 按作品、版本、章节顺序和资料类型做结构化过滤；
2. 用人物别名、实体状态、时间线和因果关系处理必须精确命中的事实；
3. 用 SQLite FTS5、中文二元/三元词和 BM25 召回正文、设定、分析与对话；
4. 合并精确命中、全文命中和最近章节，并在送入模型前再次校验版本与时间边界。

这条路径不需要新增服务，适合 1 GB 内存的 Azure 实例，也能解释每条上下文为什么被
选中。向量召回不能替代版本、章节和正史状态过滤，否则会把未来章节、旧 Tag 或已经
失效的设定混入当前写作。

## 先补检索基准

是否增加向量索引应由真实召回缺口决定，而不是由功能列表决定。基准至少覆盖：

- 人物改名、别名和称谓变化；
- 跨章物品状态、伤势、地点和知情边界；
- 相隔很远的伏笔与回收；
- 用户用近义表达查找旧事件；
- Tag、历史版本与当前 `main HEAD` 的隔离。

每个问题保存期望证据的文档 ID 和字符区间，持续记录 `Recall@5`、`MRR`、错误版本
命中率、上下文字符数、检索延迟和连续性漏检率。先加入精确实体命中、BM25、章节邻近
与因果优先级的倒数排名融合；只有融合后仍存在稳定的语义召回缺口，才进入向量阶段。

仓库内置的合成回归集可以直接运行：

```bash
python -m app.retrieval_benchmark
```

报告默认写入 `benchmark-results/retrieval/`。合成集负责阻止排名和作用域回归；是否启用
向量层仍要以真实作品查询集的结果为准。

当前实现使用倒数排名融合（RRF）合并四类信号：FTS5/BM25、完整概念命中、因果资料
优先级和章节邻近度。候选生成前先强制过滤作品、分支、当前章节之前的位置与显式排除
章节；结果携带各项排名信号，便于排查模型为什么看到了某条记忆。合成基准当前覆盖
6 类查询，Recall@5 与 MRR 均为 1.0，且未来章节、其他作品和其他分支越界命中为 0。

## 可选向量阶段

需要时采用可关闭的混合检索，而不是部署独立向量服务：

- 后台按不可变内容哈希分块并批量生成多语言 embedding；
- 向量及元数据保存在 SQLite 或分片文件中，按作品懒加载；
- 先做版本、章节和类型过滤，再做向量近邻；
- 将向量结果与精确命中、BM25 结果做排名融合；
- HEAD 改变时只重建受影响的块，Tag 直接复用相同内容哈希的向量；
- embedding 服务不可用时自动退回现有检索，不阻塞阅读和写作。

在小服务器上优先使用外部 embedding API 或离线批处理，避免常驻模型和常驻向量数据库
占用内存。只有检索基准证明收益大于成本后，才把它设为默认能力。
