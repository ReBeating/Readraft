# Readraft：产品定义、当前状态与路线

> 更新日期：2026-08-05
> 当前阶段：早期 MVP。数据格式、界面和部署方式仍可能发生不兼容变化。

## 1. 产品定义

Readraft 是开源、自托管的 AI 阅读与创作工作台，主要服务长篇中文小说的原创、续写、
改写和二次创作，阅读分析用于反哺写作。

它不把产品定义成“输入提示词，得到一段文本”，而是维护一部作品长期需要的四种关系：

1. 正文和版本：现在写到哪里，哪些历史不可变，哪个阶段已经固定；
2. 作品资料：人物、世界、结构和文风中哪些内容已经由作者确认；
3. 故事状态：正文实际发生了什么，人物知道什么，伏笔和因果走到哪里；
4. AI 协作：模型本轮看过什么、做过什么、修改了什么以及如何撤回。

正式名称为 **Readraft**，副标题为 **AI 阅读与创作工作台**。

## 2. 产品原则

- 用户主要与 AI 和正文交互，不要求理解 Agent、提示词工程或内部工具链。
- 阅读、分析和创作属于同一个作品，不拆成互不相通的首页对象。
- 只有 `main` 可写；Tag 永远只读。
- 每章只有一个 HEAD，不维护“工作稿”和“正史”两套正文状态。
- 作者明确要求写入时直接生成可撤回版本；明确要求只讨论时不写入。
- 质量检查提供修改依据，不设置统一字数门禁或强制审核流程。
- 场景是规划单位，不是另一套正文存储和组装流程。
- 参考书只提供证据化的抽象技法，不把原文措辞或具体情节交给 Writer。
- 模型、API Key 和正文由用户自己的部署控制；没有真实模型时不伪造结果。

## 3. 核心信息架构

### 3.1 作品库

首页只显示一个作品库。新建和导入是同一入口的两种来源：

- 新建作品：立即拥有可写 `main`；
- 导入文本：先生成不可变原始 Tag，用于阅读与分析；需要修改时再创建 `main`；
- main 可以随时阅读；Tag 不能新增、修改或删除章节正文；
- 任一阶段都可以从 main 打 Tag，形成“一稿、二稿、送审稿”等整书快照。

每张作品卡进入统一工作台；导出 TXT、导出作品归档和删除属于卡片辅助操作。

### 3.2 工作台

工作台由正文、作品资料、分析与笔记、版本和 AI 对话组成：

- 正文：章节目录、阅读、编辑、自动暂存和正式保存；
- 作品资料：作品概览、世界、人物、剧情与结构、叙事与文风；
- 分析与笔记：绑定具体正文版本的分析、故事记忆和作者长期笔记；
- 版本：每章 main HEAD、不可变历史和整书 Tag；
- AI：讨论、检索、整理设定、创作、修改和分析使用同一个输入框。

桌面端可同时看到目录、正文和 AI；移动端只展示当前主区域，目录和 AI 通过覆盖层打开。
阅读 Tag 与编辑 main 使用相同布局，但只读状态不会展示写入动作。

### 3.3 作品资料五类

1. 作品概览：书名、题材、故事承诺、目标读者、主题、核心吸引力、结局边界；
2. 世界：背景、规则、势力、地点、物件、能力和术语；
3. 人物：身份、欲望、动机、矛盾、秘密、关系、声音和人物弧；
4. 剧情与结构：蓝图、长期剧情线、分卷、未来章节、任务卡和场景节拍；
5. 叙事与文风：视角、时态、叙述距离、声纹、偏好、禁用表达和技法。

表单用于精确查看与手工修正，不应成为开始写作前必须填完的问卷。默认入口是对话；
AI 通过受控工具直接修改作者明确要求修改的字段，并让结果立即可见、可撤回。

## 4. 当前 MVP

### 4.1 版本与可靠性

- 每章 main HEAD、不可变父版本历史、整书 Tag；
- 手工保存、AI 创作、局部修改、撤回和恢复都走同一提交协议；
- Tag 固定正文、来源版本、哈希和当时的作品资料；
- HEAD 改变时旧分析失效，后续章节待复查，Story Memory 排队重建；
- edit buffer 绑定 base HEAD，具备单章、单用户总量和保留期限制；
- 作品归档、完整实例备份、迁移、自动更新和完整性 doctor。

### 4.2 AI 协作

- Provider 原生 SSE 和工具调用；
- DeepSeek、OpenCode Go、自定义 OpenAI、OpenAI、Gemini 与 Ollama；
- 用户维护模型列表、默认模型和 Low / Standard / Max 路由；
- 近期对话直接使用，较早对话和作品资源通过虚拟工作区检索；
- `glob/read/grep/search/diff/edit/write/patch/delete/restore` 基础工具；
- `create/compose/series/task` 小说领域动作；
- 可选 Exa 联网搜索和安全网页读取；
- 所有写入再次校验用户、作品、main、能力和 revision；
- 每轮记录工具、结果、耗时、token 与错误，但不向用户展示工具预算。

### 4.3 写作与修改

- 从全书对话直接创建第一章；
- 生成、续写、整章重写和保守润色统一经过纯文本 `compose` 管线；
- 局部精确修改使用 edit，跨同一边界的多项修改使用原子 patch；
- 明确要求连续多章时使用可断点恢复的 series；
- 写作规则集中在一个 Agent 层契约，强调场景、行动、因果、信息控制、人物声音和
  自然节奏；
- 文风审校定位具体原文并提出局部候选，不强制通过才允许保存。

### 4.4 长篇连续性

- 全书蓝图、长期剧情线、分卷、未来章节骨架、任务卡和场景节拍；
- 计划与既有事实严格分离；
- Story Memory 维护人物、关系、地点、物品、知情、剧情线、伏笔、时间和事件因果；
- 旧章修改后按章节顺序撤回和重放状态；
- FTS5 与中文稀疏检索从早期章节召回相关记忆；
- 人物与事实别名由作者确认后统一。

### 4.5 阅读分析与技法回流

- TXT/Markdown 导入预览显示候选章节、原文 offset、字数和边界置信度，并允许改名、
  合并和按光标拆分；
- 参考章节与整书对话；
- 结构、事实、叙事、文风和技法五层分析独立保存、重试和按内容哈希复用；
- 模型结论携带精确字符区间，服务端逐字回查冻结正文并可从页面返回原文；
- 全书汇总人物出场、事件时间线、伏笔生命周期、节奏分布和证据化文风画像；
- 证据化技法候选、作者改造、作用范围和原创性边界；
- 参考书全书文风画像以只读虚拟资源提供给 Agent，只有作者明确要求参考文风时读取；
- 只有作者启用后的抽象技法进入规划、正文或文风审校。

## 5. 已删除的设计

以下概念不再是运行时架构，也不应重新通过隐藏页面或兼容字段引入：

- 旧版章节编辑器、任务卡页、场景工作台和独立作品聊天页；
- 逐场景正文版本、场景审校、场景组装；
- 统一字数硬下限、独立硬审核和“审核通过才算正文”；
- AI 工作稿指针、正史指针和作者二次晋升；
- 固定 JSON 决策循环、无工具回退 Agent 和服务端强制下一工具；
- 让通用 write 工具承载长篇章节正文。

已发布迁移中的旧表名必须保留，使旧数据库能顺序升级；它们是数据历史，不是兼容
实现。最新迁移会删除已经退出运行时的表、列和触发器。

## 6. 当前不足

1. `main.py`、`db.py` 和对话服务仍偏大，虽然视图构建、写作上下文和对话上下文已开始
   拆分，路由与 repository 还需要继续按稳定事务边界提取。
2. 真实 Provider 的自动化测试以协议 mock 为主；每次正式发布前仍需在稳定加密密钥的
   部署环境完成真实流式写作冒烟。
3. 参考分析已经具备五层结果与全书文风画像，但还没有用真实长篇小说建立跨模型的
   证据准确率、标签稳定性和作者可用性基线；人物弧与因果链的跨章归并也仍较基础。
4. 不相关作品之间还没有“绑定一个全书文风画像”的产品动作；当前可靠路径是让作者
   选择具体抽象机制，保存为技法卡并绑定到目标作品，避免整书风格被静默套用。
5. 长篇质量基准已经可以重复运行，但当前离线分数不能替代真实模型盲评；仍需跟踪
   连续性错误率、人工修改量、费用和
   延迟数据，而不是只凭一次生成观感。
6. 1 GB VM 不适合默认常驻向量数据库；当前使用 FTS5 与稀疏召回，是否增加可选向量
   后端必须由真实召回评测决定。

## 7. 路线

### P0：发布前收口

- 继续按 workbench、assistant、reviews、repositories 拆分大模块；
- 让 README、产品文档、模板和代码只使用当前术语；
- 把 doctor、迁移、完整备份恢复与真实 Provider 冒烟加入发布检查表；
- 用浏览器验证桌面和移动端的新建、导入、写作、撤回、Tag 与只读路径；
- 明确标记早期版本，不承诺数据格式向后兼容。

### P1：拆书成为写作基础设施

已完成基础设施：

- 导入预览、边界置信度和人工改名/合并/拆分；
- 结构、事实、叙事、文风、技法五层单章分析与逐字证据校验；
- 内容哈希缓存、独立层重试、人物/事件/伏笔/节奏与文风的全书聚合；
- 从技法层建立带来源和原创性边界的技法卡；
- Agent 按作者明确意图读取只含抽象规则的全书文风画像。

下一步验收：

- 使用用户提供的真实小说跑完整分析，抽样复核证据、错误事实与跨章标签漂移；
- 比较不同章节规模和不同模型下文风画像的一致性；
- 让作者选取画像中的规则生成原创章节，以盲评和修改量判断它是否真的可用；
- 在证据成立后再设计跨作品“参考画像绑定”，且默认关闭、可见、可撤销。

### P2：写作质量与长篇评测

- 建立公版材料和合成作品组成的可重复评测集；
- 比较 Low / Standard / Max 的成文质量、连续性、延迟与成本；
- 跟踪作者接受率、撤回率、局部修改量和长篇状态错误；
- 基于评测调整写作包、检索和模型路由，而不是增加更多固定工作流；
- 只有稀疏检索召回不足且可量化时，提供可选向量索引。

### P3：多人和生态（非当前范围）

多人实时协作、移动原生客户端、插件市场、云托管账号、模型代付和出版流程集成都不是
早期 MVP 的发布条件。它们必须在单作者、自托管、长篇闭环稳定后再评估。

## 8. 成功标准

Readraft 的优势不能用页面数量证明。一次有效的产品验证至少观察：

- 新用户能否不看说明完成新建/导入、与 AI 讨论、写一章、修改、撤回和打 Tag；
- AI 是否把内容写到正确章节和正确资料字段；
- 连续多轮后能否从历史中找回作者早期要求；
- 修改旧章后，后续状态和检索是否正确失效与重建；
- 参考书技法是否有证据、足够抽象且不会复刻原作；
- 正文是否比“直接把整书塞给模型”更连贯，人工返工是否更少；
- 备份、恢复、升级和 doctor 是否能在不丢失正文与凭据的情况下通过。

只有这些指标稳定，产品才从“基本能用”进入“可以信任”。
