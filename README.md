# 叙枢

叙枢（Xushu Studio）是一套面向长篇中文小说的轻量 Web 创作工作台。它把设定、全书规划、章节正文、故事记忆、编辑审校与 AI 共创组织在同一个创作空间中。用户登录后可以建立小说项目、确认全书蓝图与长期剧情线、维护设定和人物卡、规划分卷/章节/场景，并使用自己的 DeepSeek API Key 生成初稿、续写、重写或润色正文。

Codex 暂未接入。拆文能力作为辅助研究工具服务创作：逐章分析可以提取可迁移技法，作者保存、改造并主动绑定后，系统才会在对应的规划、正文创作或审校任务中读取这些抽象规则。

## 已实现

- 用户注册、登录、签名 Cookie 会话与 CSRF 校验
- 每个账号独立的 DeepSeek API Key、模型、思考模式与全局系统提示词；可用 Key 直接从 DeepSeek 接口读取当前可用模型
- API Key 认证加密保存，不写入 Cookie、不完整回显
- 新版创作工作台：横屏为目录 / 固定页幅正文 / AI 共创三栏，左右面板均可收起；竖屏只显示当前页，目录与 AI 以覆盖层打开
- 新建作品不要求先填书名或表单，直接进入设定工作台；书名、题材、故事核心、目标读者、叙事约束和默认单章篇幅都可先与 AI 讨论，再由作者确认写入
- 正文在固定页幅内独立滚动并自动保存；到达章节边缘后继续滑动可切换上一章或下一章
- 白天与低眩光夜间两套配色在首页、正文和设置页保持一致，并在本机记住选择
- 全局系统提示词与本书补充指令按“基础能力边界 → 全局偏好 → 本书偏好”注入正文生成和共创对话
- 小说项目：作品承诺、目标读者、核心吸引力、结局约束、世界设定、文风与叙事视角
- 全书蓝图：核心悬问、主角长期目标、冲突引擎、开篇/终局状态、关键转折、必须兑现项与禁止捷径
- 主线、支线、人物弧光、关系线、谜团线和世界线的长期规划；每条线可维护优先级、阶段、悬问、承诺、起止状态、人物和计划转折
- 蓝图与规划剧情线使用不可变修订；草稿不会改变模型上下文，只有作者确认版才会生效，历史版本恢复时也只创建新草稿
- DeepSeek Story Planner 可按“建立 / 优化 / 重想未来”三种模式生成恰好三套实质不同的全书方案；每套包含完整蓝图、3–8 条剧情线、优势、代价与只读分卷草图
- 全书方案使用请求时冻结的确认计划、正史、人物知情边界和项目级抽象技法；结果只供比较，可局部、重复采纳为新草稿，绝不自动确认、创建正史或创建分卷
- DeepSeek 滚动结构 Planner 在作者确认蓝图与主线后，严格生成三套可比较的未来结构；每套包含 2–6 卷和连续 10–30 章的作用、推进线、关键事件与章末钩子
- 采纳滚动结构前显示精确的新建、更新与保留清单；只改正史之后的分卷、章节骨架和任务卡草稿，正文、候选版本与正史指针不在改动范围内
- 生成后若确认蓝图、长期剧情线、正史、人物或其他结构基线发生变化，系统会拒绝旧方案；刚采纳且尚未继续编辑的结构可安全撤销
- 采纳后作者可逐卷修改目标、冲突与回报，也可逐章修改卷属、结构职责、关键事件、推进线与章末推动；正史范围锁定，受影响任务卡退回草稿，已有场景稿标记过期
- 作品工作台提供只读的全书结构体检：扫描正史边界后的全部未来骨架，确定性检查章节/卷序、骨架必填证据、确认剧情线精确引用、职责连续段、卷内反转与兑现，以及主线空窗
- 结构体检保留每章来自哪次滚动结构采纳或作者手改的来源，自动建立“正史 → 未来”“旧窗口 → 新窗口”“结构方案 → 作者接管”等接缝；来源变化本身不是错误，只有可举证的硬切线、同卷重复建立或跨卷未收束才提示
- 作者可在结构体检中显式建立“较早章 cause → 较晚未来章 effect”的因果链接，支持因果触发、条件铺垫、后果升级和兑现回收；链接可跨剧情线或滚动窗口，并可解释原本的硬切线
- DeepSeek 因果审查器可在作者指定的未来 2–80 章内，只读对照确认正史、人物知情、连续性账本、章节骨架、剧情线、窗口接缝和已有链接；结果最多 8 条且必须携带两端证据，也允许明确返回零条，不会为了凑数强连
- 同一可观察结果存在多项可信前因时，审查器会把 2–4 条候选组成可比较解释组；每项分别显示反证或证据缺口、可推翻条件和仍缺的中间步骤，并标明这些解释互斥、可并存或现有证据无法判断
- 新版因果候选必须对正史事实、人物知情、时间先后、世界规则和连续性完成五类证据引用式预检；每项只能引用冻结目录中的精确证据 ID，并明确区分“有证据支持 / 证据不足 / 发现冲突”，不会把模型判断伪装成事实
- 每条候选会按精确剧情线 ID 推演变化前后、影响类型、风险和所需承接章节；跨线候选必须覆盖两端涉及的全部已确认剧情线，避免只推进目标线却无意破坏起因线
- 因果建议保存请求时的冻结快照和基线指纹；作者可逐条编辑起因/结果后确认或忽略。比较组必须先确认已核对其他解释；仍缺中间步骤时必须记录补写安排；语义冲突还必须记录作者覆盖理由或先修改规划。确认才原子地建立链接，相关基线发生变化时旧建议不能采纳
- 任一仍待审的新版因果候选都可继续启动未来 10–30 章的长期沙盘；系统固定返回“最小改动、分散后果、压力测试”三种实质不同分支，逐章引用冻结证据，检查人物知情、确认剧情线和蓝图必须兑现项。沙盘本身只读；作者先独立采纳原因果链接后，才可把一条分支转成逐章待审落地清单
- 分支落地清单允许作者逐章改写任务要求、选择确认剧情线、伏笔铺设/回收，并分别决定采用或拒绝；全部审完后才原子更新未来骨架与任务卡草稿，使相关场景稿过期。正文、候选版本、正史和原因果链接不在改动范围内；应用后未继续编辑时可安全撤销
- 未来因果链接只进入相关章节的 Planner、整章 Writer 与 Scene Writer；修改或归档会使相关未来任务卡退回草稿，但不改正文或正史。目标章进入正史后，链接退出生成上下文，由实际 Story Delta / Memory 因果接管
- 人物卡：定位、性格、背景与人物弧光
- 分卷目标、未来 10–30 章滚动规划和章节任务卡
- 结构化录入读者意见，由 Planner 严格生成三种带满足点、牺牲和风险的未来走向
- 读者意见不会进入 Writer；只有作者采纳的安全方案才会更新未来章节骨架和任务卡
- 每章 2–5 个场景节拍；任务卡未经作者确认不能生成正文
- DeepSeek Planner 提出可编辑的任务卡草稿，作者确认后才交给 Writer
- 已保存的作者任务卡可走“只拆场景”路径：章节级字段被冻结，Planner 只能生成 2–5 个场景，并把每条推进线、必做事件、伏笔和章末钩子逐字映射到具体场景；缺项不能确认，运行期间基线变化会拒绝旧结果
- 场景工作台支持逐场景生成、重写、手工保存和恢复历史版本；场景计划变化后旧稿自动标记为过期
- Scene Auditor 在组装前核对正史、人物知情、世界规则、当前节拍和相邻场景边界
- 只有全部场景通过审校或由作者记录原因覆盖后，才能按任务卡顺序组装为新的章节候选稿
- 章节执行状态机统一显示“任务卡—正文候选—硬审计—去 AI 味—正史—故事记忆”六步进度，并把作品工作台和各写作页面指向当前最安全的下一步
- 新建作品即使还没有章节，也会显示置顶的“开始写作”卡片，可直接规划第一章，或按需先比较全书方案、建立作品声纹
- 正史 Story Delta 自动提取失败、缺失或被作者拒绝后，可从当前正史版本安全重试；重试仍只产生待审核提案
- AI 写作：场景初稿/重写，以及整章初稿、续写、重写和保守润色
- 持久化 AI 创作对话：可按全书或本章讨论构思、检查与改写；复用个人 DeepSeek Key，并保存连续对话历史
- 工作台只保留一个聊天输入框，不向作者暴露 Agent 角色或模式。用户只需表达“交流想法 / 整理设定 / 创作正文 / 修改正文 / 分析作品”五类目标；系统内部再把故事规划拆成独立原子任务，并按本轮实际任务授予最小工具权限
- 模型先输出受 Schema 约束的本轮任务、置信度、目标章节和可选任务链；服务端再结合当前页面、对话范围、引用、设定状态和目标章节裁决内部执行器与工具权限。页面只是强先验，作者明确目标优先；低置信度或不满足写入条件时回退到交流
- Agent Loop 不再把“6 步”混成一个硬限制：常规模型轮次最多 10 次，成功工具调用最多 6 次，无效调用最多 2 次，最后的禁止工具收束回合单独计算。重复同一调用会立即熔断，写入候选成功后立即收束；即使模型没有按要求结束，也会根据已有结果返回保底答复
- 从全书对话直接要求创作第一章时，若作品尚无章节，服务端会先创建未命名空章节、把对话绑定到该章，再授予创作工具；明确创作目标尚未真正调用写作工具时，模型不能只靠文字声称已经完成
- 已实现的领域工具包括读取作品设定、读取当前章节、检索故事记忆、读取/检索参考章节、读取拆书分析、提出设定候选、提出版本化全书规划、创建章节工作稿和修订正文选区
- 每次模型决策与工具调用都记录内部任务、可用工具、动作、结果、耗时、token、参数和错误；越权、重复与失败调用会被服务端拦截并保留审计记录，失败回复中也能展开查看
- 参考作品分析只能读取和检索参考原文、拆书分析并提炼带证据的抽象方法；正文创作只读取作者绑定后的技法卡，不接收参考作品的独特措辞、专有名词或具体情节
- 章节编辑器可引用当前不可变正文版本中的选区提问；服务端校验版本、内容哈希和起止位置，回复依据可回跳原始版本
- 创作和修订完成后自动提交到可撤回的工作稿：每次提交形成带父版本的不可变记录，撤回也创建新的反向提交；设定候选和进入正史仍需作者确认
- 自动提交不会确认正史、修改任务卡或写入 Story Memory；这些边界由服务端权限与事务校验保证，不依赖模型自述
- 拆书文档也可按整本或参考章节发起对话；参考原文只用于抽象讨论结构与技法，不能从对话生成可应用的正文改写
- 章节 Planner 读取全部已确认且未放弃的全书规划，以及作者为本章建立的未来因果约束；Writer 只读取蓝图、本章任务卡精确选中的规划剧情线和与本章直接有关的因果链接，避免每章同时推进所有支线
- 生成时自动带入作品承诺、确认版全书蓝图、本章选中剧情线、作者确认的本章因果约束、卷目标、人物卡、前一章正史末尾、已确认任务卡与 Story Memory
- 确认版蓝图发生变化时，未来已确认任务卡会退回草稿；确认版剧情线变化只让引用该精确标题的未来任务卡待复查
- SQLite FTS5 从更早章节补充检索与当前任务相关的作者确认 Memory；严格限制为本作品、当前正史分支和当前章之前
- 最近 5 章走固定上下文而不重复检索；任务页展示检索概念、命中章节、记忆类型和匹配依据
- 作者确认 Story Delta 后按章节顺序自动重放人物状态、关系、地点、物品、人物知情、剧情线/承诺、伏笔生命周期与故事时间，并保存逐章状态快照
- Story Delta 支持稳定的 `canonical_fact`、`event_key` 与 `cause_event_keys`；事件可以引用此前已发生事件，形成可核对的直接因果链
- 作者可把“女主 / 林记者 / 林岚”等人物称呼，或两种事实表述，归到同一记忆身份；保存规则后立即重放当前正史，FTS5 查询也会自动扩展已确认别名
- “变化前”声明与既有正史不一致、人物遗忘缺少知情基线、已关闭剧情线继续推进或已回收伏笔再次使用时，生成可追溯的连续性问题
- 事件引用不存在的前因会产生待核对项，自我引用或同一事件键指向不同事件会产生硬冲突
- 作者可以记录有意安排，但问题不会被静默删除；Planner、Writer 和审校器仍会看到该判断
- 替换旧章正史会在同一事务中撤回旧状态、重放仍有效的后续 Delta，并把最新状态与问题送入 Planner、Writer 和审校器
- 忽略空白后的正文硬下限为 2000 个字符；不足时只进行一次定向补写
- 独立 Hard Auditor 核对正史事实、人物知情、世界规则、任务卡、场景、禁止事项和视角
- 审计不通过的候选稿仍会保留，但不能直接进入正史；作者覆盖时必须记录原因
- 每部作品可维护可执行声纹：叙述、句段、对话、意象、比喻、留白、偏好和禁用表达
- 作者可粘贴自己拥有权利的样章，由 DeepSeek 提出带精确原句证据的声纹建议；无证据规则会被丢弃，建议不会自动覆盖当前声纹
- 作者可逐项改写提取结果并保存为草稿或确认版；只有确认版声纹才会进入整章 Writer、Scene Writer、Style Auditor 和写作上下文快照
- 作者手工保存章节或场景的新版本后，可主动要求系统从这次改稿中归纳长期偏好；模型候选必须绑定实际差异中的逐字证据
- 手工改稿候选不会自动生效；作者逐项改写并确认后，只有类别、抽象规则和适用范围会进入 Writer 与审校上下文，剧情证据原文不会进入
- 独立“编辑记忆”页会按类别整理来自不同手工改稿的确认规则；作者至少选择两次独立改稿作为支持，也可标注冲突/例外并编辑最终适用边界，系统不会自动合并
- 稳定偏好启用后会折叠关联的支持与冲突单次规则，避免 Writer 同时收到重复或矛盾指令；停用稳定偏好后，仍启用的原始规则会恢复
- 稳定偏好可查看确认前后的相关 AI 味问题观察率；统计按正文去重、使用同一审校器并设置最小样本，只展示同期趋势，明确不把相关性宣称为规则效果或因果
- 作者可以随时停用已经确认的单次规则或稳定偏好，后续写作上下文会立即更新
- Style Auditor 最多定位 12 个有唯一原文位置的 AI 味问题；同段重复引文无法唯一定位时不会贸然改写，也不会自动全文洗稿
- 作者选中问题后生成恰好两个局部改写候选，并查看字符级差异
- 接受定点改写会创建新正文版本并重新进入硬审计；忽略和接受选择会沉淀为作者偏好
- 候选稿与正史版本分离；作者可对任意两个最近整章版本查看新增、删除与完整对照，再接受或恢复历史版本；修改旧章会标记后续章节待复查
- 替换既有正史前先生成影响报告；作者逐项决定保留、复查、改写未来章节或退役剧情线后才能切换
- 正史确认后由 Observer 提取 Story Delta，作者审核后才投影人物状态、事件、知情、剧情线和伏笔
- 拆文分析可提取带来源证据、适用范围、执行规则和原创性边界的技法建议
- 个人技法库支持手动建卡、编辑、归档，并追溯到来源文档、章节和分析
- 技法卡可绑定到全书、分卷、章节或场景，并分别控制是否用于规划、正文或 AI 味审校
- 创作模型只接收作者启用后的抽象规则、作者改造和原创性边界；参考观察、原文措辞和具体情节不进入 Writer
- 每次写作任务保存实际上下文快照，便于复现和审计
- 版本化 SQLite 迁移，不删除现有账号、API Key 或作品数据
- 正文编辑器、字数统计和 TXT 全文导出
- 单进程持久生成队列；服务重启后自动重新排队未完成任务
- 原有 TXT/Markdown 导入、自动拆章和结构化分析工具

## 本地运行

需要 Python 3.9+。

```bash
cd xushu-studio
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

打开 <http://127.0.0.1:8000>，注册或登录后：

1. 在“API 设置”中填写个人 DeepSeek API Key。
2. 在首页直接“新建作品”。系统会进入设定页，不要求预先填写书名。
3. 在右侧对话框说出人物、画面、题材或阅读感受；需要时把 AI 整理出的候选设定应用到作品，再在六个设定分类中继续修改。
4. 从左侧目录新建章节，或直接要求 AI 创作第一章。空白章节会先讨论写作思路；明确要求创作后，正文才会提交到可撤回工作稿。
5. 正文会自动保存。选择一段文字后直接向 AI 提问，可以分析、局部修订或继续写作；引用依据会回到对应不可变版本。
6. 不需要选择 Agent 或工作模式。服务端会结合当前页面、引用和明确要求，在交流想法、整理设定、创作正文、修改正文与分析作品之间调度。
7. 可选：上传参考文本到只读参考书库，执行逐章拆解、和 AI 讨论结构与技法，并把抽象方法保存为技法卡。
8. 主导航只展示日常工作台。全书规划、场景拆分、连续性、硬审计、正史和编辑记忆等高级能力仍保留在服务端与受测试覆盖的专用流程中，后续再逐步整合进统一工作台。

管理员也可以在 `.env` 中设置共享 Key：

```dotenv
DEEPSEEK_API_KEY=你的_api_key
DEEPSEEK_MODEL=deepseek-v4-flash
```

调用顺序为：个人 Key 优先、服务器共享 Key 次之、开发环境 mock 最后。生产环境如果没有可用 Key，会要求用户先进入 API 设置，不会生成假正文。

## DeepSeek 写作行为

应用调用：

```text
POST https://api.deepseek.com/chat/completions
```

整章 Writer 和 Scene Writer 使用普通文本输出；全书 Story Planner、滚动结构 Planner、跨章因果审查器、长期因果分支模拟器、章节 Planner、锁定任务卡的 Scene Planner、样章声纹提取器、手工改稿偏好提取器、读者意见 Planner、Scene Auditor、Hard Auditor、Observer 和拆文工具使用 JSON Output 与 Pydantic 结构校验。全书 Story Planner 必须返回三套完整且实质不同的方案；请求时会冻结确认版全书计划、正史、人物知情边界和启用的项目级抽象技法，模型结果保存到独立持久队列，采纳时也只新增未确认草稿。滚动结构 Planner 同样固定返回三套方案，并把每套限制为 2–6 卷、连续 10–30 章；应用时再次核对冻结的确认基线与当前结构指纹，只允许更新正史之后的规划数据。跨章因果审查器最多返回 8 条带双端证据的候选，也允许返回零条；候选只能引用冻结快照里的章节与证据 ID。同一结果有多项可信前因时，模型必须用零基索引组成 2–4 条解释组，并为每项提供反证或证据缺口、可推翻条件和中间步骤就绪状态。每条新版候选还必须完成五类语义预检，并用精确确认剧情线 ID 给出联合影响；服务端会逐项验证引用。待审候选可进一步触发只读的 10–30 章沙盘，严格得到三种分支，并对章节标题/位置、人物名、剧情线、蓝图回报和证据 ID 做服务端边界校验。沙盘不能直接应用；原因果链接经作者单独确认后，所选分支才能被确定性拆成逐章任务补丁。每项都需作者编辑并接受或拒绝，最终应用仍会重检未来边界、任务卡指纹和运行中任务。逐章补丁写入任务卡草稿后，Scene Planner 可以冻结当前任务卡，只替换场景节拍；服务端要求每项推进线、必做事件、伏笔和钩子都有逐字场景引用，并在落库前再次比较完整任务卡指纹。作者确认已比较其他解释、核对语义和跨线影响、处理仍缺步骤，并在冲突时留下覆盖理由之前，系统不会写入任何链接。章节 Planner 会读取作者确认的全书蓝图、全部有效规划剧情线和与本章直接有关的作者因果链接，并要求用精确标题选择本章要推进的线；Writer 只读取这些被任务卡选中的线及本章的 incoming / outgoing 因果约束。写前计划和未来因果始终作为方向与边界，不能被模型当成已经发生的正史，也不能提前兑现目标章结果、后续转折或终局。声纹证据会在服务端逐字回查作者样章；改稿偏好证据还必须存在于两个不可变版本的实际差异块中。无法定位的引文不会进入建议。个人设置可以选择模型并开启思考模式。API 地址只能由服务器环境变量配置，网页用户不能指定任意 URL，避免服务器端内网访问风险。

个人 API Key 使用 Fernet 认证加密后保存在 SQLite。默认从 `APP_SECRET_KEY` 派生加密密钥；生产环境建议单独设置稳定的 `APP_CREDENTIAL_ENCRYPTION_KEY`。修改该密钥后，已有用户需要重新填写 API Key。

## Azure 部署

低内存 VM 必须保持：

- `uvicorn --workers 1`
- 应用内 AI 并发为 1
- Uvicorn 只监听 `127.0.0.1:8010`
- 仅通过 Nginx 或 Azure 托管入口的 HTTPS 对公网开放

示例文件：

- `deploy/xushu-studio.service`
- `deploy/nginx.conf`

生产环境至少设置：

```dotenv
APP_ENV=production
APP_SECRET_KEY=<至少 32 字节随机值>
APP_CREDENTIAL_ENCRYPTION_KEY=<至少 32 字节且长期保持不变>
APP_COOKIE_SECURE=true
APP_ALLOW_REGISTRATION=false
# 可选；留空时每位用户在网页中填写个人 Key
DEEPSEEK_API_KEY=
```

部署前创建专用账号和数据目录：

```bash
sudo useradd --system --home /opt/xushu-studio --shell /usr/sbin/nologin xushu
sudo install -d -o xushu -g xushu -m 700 /opt/xushu-studio/data
sudo chown root:xushu /opt/xushu-studio/.env
sudo chmod 640 /opt/xushu-studio/.env
```

后台队列与 Web 服务同进程，因此只能启动一个 Uvicorn worker。进程锁会拒绝第二个实例，避免同一生成任务被重复执行和计费。
